# Solusi memori BLE dual-board

Status: profil build pasangan mengunci BLE di C3, 6 Oktober 2026. Advertising C3 berhasil pada bench tetapi cadangan RAM gagal memenuhi kebutuhan beban gabungan; validasi ponsel masih menunggu. Uji BLE-only pada S3 memicu brownout dan firmware penuh S3 telah dipulihkan.

## Fakta dari pengukuran sebelum profil terbaru

- Arduino-ESP32 3.3.11 memakai NimBLE untuk C3. Mengganti nama wrapper BLE saja tidak menjamin penghematan.
- C3: free heap sebelum Wi-Fi 172.672 byte, sesudah Wi-Fi 124.388 byte, sesudah startup gateway/UART/task 77.364 byte. Percobaan memulai BLE kemudian abort di `std::bad_alloc -> BLEService::createCharacteristic`.
- Sampel sebelum perubahan profil melalui dashboard: C3 internal free 52.936 byte, largest block 42.996 byte, minimum historis 21.116 byte, tanpa PSRAM. S3 internal free 56.532 byte, largest block 31.732 byte, PSRAM free 4.427.384 byte. Sampel ini tidak mengukur biaya BLE karena BLE belum aktif.
- Guard BLE 150.000 byte mencegah crash, tetapi membuat BLE selalu tidak aktif pada konfigurasi C3 saat pengukuran tersebut.
- SDK NimBLE: 3 koneksi, 8 CCCD, 64 ATT prepare entries, 4 GATT procedures, host stack 5.120 byte, MSYS1 12 x 256, MSYS2 24 x 320, ACL 24 x 255, event high-priority 30 x 70. Angka ini adalah konfigurasi, bukan pengukuran total biaya BLE.
- Stack task ESP-IDF dalam proyek ini dihitung dalam **byte**: board link 6.144, phone command 4.096, TLS worker 8.192 saat aktif. Mengurangi stack pertama dan kedua ke 4.096/3.072 hanya memberi sekitar 3 KB; pengurangan membutuhkan pengukuran high-water mark.
- Buffer RPC 12.289 byte, UART RX/TX 4.096/2.048 byte, TX queue 8 frame sekitar 8,3 KB (Frame 1.036 byte). Batas RPC atau queue tidak boleh diperkecil sebelum payload/status/settings/audio/update terbesar diuji.
- Buffer aplikasi BLE bukan konsumen terbesar: packet queue sekitar 2,4 KB dan fragment/pending buffers sekitar 2,4 KB.

## Rekomendasi

BLE tetap di C3. Build saat ini memilih adapter NimBLE-Arduino 2.5.1 dengan host yang dikompilasi dari source dan konfigurasi terpin; SDK khusus tetap merupakan opsi alternatif:

1. **SDK Arduino/ESP-IDF khusus:** mempertahankan API BLE yang ada, membangun ulang host/controller dengan sdkconfig yang dipin. Ini mengurangi perubahan kode keamanan, tetapi menambah pekerjaan toolchain dan pemeliharaan SDK.
2. **Adapter NimBLE-Arduino 2.5.1:** menyediakan host yang dibangun dari source serta konfigurasi koneksi, MTU, pool, dan alokasi. API callback/keamanan/ANCS perlu disesuaikan dan diuji. Rilis stabil yang diperiksa adalah 2.5.1; hindari master 3.0.0-dev untuk percobaan produksi ini.

Audit build sudah memilih adapter source-host. Konfigurasi harus berlaku ke seluruh host yang dikompilasi. Jangan hanya mendefinisikan `CONFIG_BT_NIMBLE_*` pada sketch sementara memakai library SDK precompiled dengan konfigurasi berbeda.

Penghematan belum diukur dan keberhasilan C3 dengan seluruh fitur belum terjamin. Profil harus menyisakan anggaran TLS/dashboard, bukan sekadar berhasil advertising.

## Opsi alternatif yang diuji: BLE pada S3

S3 pernah dipertimbangkan bila heap C3 tidak cukup untuk Wi-Fi/TLS. Namun uji BLE-only di S3 yang tersedia memicu brownout berulang saat startup. Karena itu S3 tidak menjadi pemilik BLE pada profil produksi saat ini; pertimbangkan kembali hanya setelah masalah suplai/daya S3 diukur dan diperbaiki.

- Gunakan PSRAM S3 untuk alokasi host yang mendukung external allocation; controller/DMA dan kebutuhan internal tetap harus dianggarkan.
- S3 juga hanya punya sekitar 56 KB internal bebas sekarang. PSRAM tidak otomatis dipakai oleh stack BLE internal; perlu profil alokasi yang benar atau pemindahan buffer CPU ke PSRAM.
- Pindahkan otoritas pairing/peer/bond ke S3, serta proxy dashboard untuk status, pairing/revoke dan pengaturan. Notifikasi/navigasi/command harus tetap diproses oleh satu pemilik. Hindari dua bridge yang mengklaim peer berbeda.
- Uji BLE S3 perlu mengukur konsumsi daya/rail dan BOD setelah masalah listrik ditangani. Hasil BLE-only saat ini memicu BOD; PSRAM tidak menyelesaikan masalah suplai daya.
- Jalur ini memerlukan perubahan arsitektur lebih besar dan tidak dipakai dalam build pasangan sekarang. BLE tetap dimiliki C3; status runtime C3 masih menunggu pengujian perangkat.

## 2026-10-06: ANCS queue allocation and shutdown safety

- The ANCS event queue still holds 8 events and accepts notification fragments up to 384 bytes. Each queue entry now stores metadata and an optional payload pointer; payload bytes are allocated only while a notification event is queued and released after consumption. Queue-full and allocation failures follow the existing overflow/retry path. This avoids reducing ANCS payload limits or queue depth.
- The queue admission gate closes before listener unregister/drain/delete and waits for active enqueue operations. Reset uses the same gate while draining. Review found no remaining confirmed ownership/shutdown defect. A low-confidence stale discovery callback after reset could still be accepted if the old connection handle is rapidly reused; callback/session-generation isolation remains a verification item.
- `tests.test_ble_profile` and `tests.test_dual_board_contract`: 35 tests passed. These tests include source-contract checks for allocation/free paths and admission shutdown; they do not execute a real concurrent FreeRTOS/NimBLE callback race.
- Production pair compiled successfully: C3 gateway 1,862,128 bytes / 66,592 bytes globals; S3 robot 2,090,704 bytes / 118,960 bytes globals. Diagnostic C3 image 1,862,416 bytes / 66,600 bytes globals. All fit their application slots.
- Diagnostic C3 was flashed to app0 with hash verification; NVS was preserved. BLE advertising ran for 75 seconds with Wi-Fi STA and UART link active, AP setup released after the 30-second stable window, qmax=2/8, and no brownout/panic.
